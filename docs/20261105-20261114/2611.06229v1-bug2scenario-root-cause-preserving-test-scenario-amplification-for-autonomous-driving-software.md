## 摘要
基于仿真的模糊测试通过反复变异并执行场景来暴露自动驾驶系统（ADS）故障，但将一个失败转化为可复用的回归场景仍然困难。此类变体用于检验相关机制在软件变更后是否仍然存在，例如改变天气或交通参与者位置，同时保留碰撞中的交通参与者-路线冲突。我们提出 Bug2Scenario，一个根因引导的模糊测试后框架。它从场景数据、执行轨迹和测试预言证据中提取根因模式。LLM 针对交通参与者、任务、路线和天气提出语义变体。确定性规则构建与 DriveFuzz 兼容的场景。执行证据和人工审查评估保持性。将这些职责分离可防止流畅性、语法或重复出现的标签被误当作因果证据。在匹配种子、六种 LLM 骨干模型、候选预算和执行流水线条件下，Bug2Scenario 将严格保持率提高 6.7 个百分点（p=0.104；不显著），并将含边界保持率提高 10.6 个百分点（p=0.011）。反馈有助于一些最初未成功的种子生成严格保持的候选场景。随后种子级停止可避免进一步的 API 调用和模拟器运行。剩余失败反映了交通参与者放置约束、模拟器不稳定以及因果证据不完整或相互冲突。因此，Bug2Scenario 能生成可靠的 ADS 回归资产。我们的实现见 https://github.com/YgcCoder/Bug2Sce。

## Abstract
Simulation-based fuzzing exposes autonomous driving system (ADS) failures by repeatedly mutating and executing scenarios, but converting one failure into reusable regression scenarios remains difficult. Such variants test whether the mechanism persists after software changes, for example by varying weather or actor placement while retaining a collision's actor-route conflict. We present Bug2Scenario, a root-cause-guided post-fuzzing framework. From scenario data, traces, and oracle evidence, it extracts a root-cause pattern. An LLM proposes semantic variations over actors, missions, routes, and weather. Deterministic rules construct DriveFuzz-compatible scenarios. Execution evidence and manual review assess preservation. Separating these responsibilities prevents fluency, syntax, or recurring labels from masquerading as causal evidence. Under matched seeds, six LLM backbones, candidate budget, and execution pipeline, Bug2Scenario improves strict preservation by 6.7 percentage points (p=0.104; not significant) and boundary-inclusive preservation by 10.6 points (p=0.011). Feedback helps some initially unsuccessful seeds yield a strictly preserved candidate. Seed-level stopping then avoids further API calls and simulator runs. Remaining failures reflect actor-placement constraints, simulator instability, and incomplete or conflicting causal evidence. Bug2Scenario thus produces reliable ADS regression assets. Our implementation is available at https://github.com/YgcCoder/Bug2Sce.

- **研究背景**：基于仿真的模糊测试（如 DriveFuzz）能够在 CARLA、Autoware 等环境中反复变异并执行场景，从而暴露自动驾驶系统（ADS）的碰撞、闯红灯、车道侵入、卡死等故障。但“发现故障”只是测试的开始，工程上还需要把一次失败转化为可复用、可审计的回归测试场景。
- **核心问题**：现有工作大多关注“发现新失败”，而模糊测试后扩增（post-fuzzing amplification）需要回答：哪些受控变体仍保留原始失败的**根因机制**？论文指出，仅匹配故障标签（如碰撞 C、闯红灯 R）不足以证明机制保持；同一标签可能来自不同交互，而接近行为边界的场景可能保留关键交互但症状减弱。
- **关键区分**：论文区分“症状复现”（symptom recurrence）与“机制保持”（mechanism preservation）。故障 oracle 只是检测规则，输出一次运行中的 C/R/L/S 标签；机制保持还要求保留种子的关键交互与失败进展，例如“交通参与者部分阻挡自车路线→自车进入冲突区域→规划/控制未能避让→碰撞”。
- **整体含义**：Bug2Scenario 是一个**根因引导、验证器为中心**的模糊测试后框架，将一次 DriveFuzz 发现的失败扩增为一组可执行、可追溯、根因保持的回归候选场景；其目标不是发现任意新故障，而是生成可审计的回归资产，用于调试、回归测试和维护。

## 2. 方法论

### 2.1 核心思想

- **职责分离**：LLM 只负责语义理解、因果假设和高层场景变体提议；确定性规则负责将高层变体具体化为 DriveFuzz 兼容 JSON；执行证据与人工审查负责判断机制是否保持。这样可避免“语言流畅”“JSON 可解析”“标签重复出现”被误当作因果证据。
- **三阶段流程**：
  1. **语义理解**：从种子失败中抽取结构化证据，形成根因模式。
  2. ** grounded generation**：在根因模式约束下生成高层变体，并由规则具体化。
  3. **执行验证**：预执行检查 + DriveFuzz/Autoware/CARLA 执行 + 后执行分类 + 人工保持性判定。
- **迭代反馈**：失败记忆与控制模块保存历史失败记录、构造提示、规则过滤，并通过种子级停止控制 API 与仿真成本。

### 2.2 问题形式化

- DriveFuzz 风格场景配置表示为  
  \(T = \langle Map, Mission, Actors, Puddles, Weather \rangle\)。
- 种子失败案例表示为  
  \(F = \langle T_{fail}, O, Tr, E \rangle\)，其中 \(O\) 为 oracle 结果（C/R/L/S），\(Tr\) 为执行轨迹，\(E\) 为根因证据。
- 目标是生成候选场景集合  
  \(T' = \{T'_1, T'_2, \ldots, T'_n\}\)，每个 \(T'_i\) 仍是 DriveFuzz 风格配置，并在变化场景条件的同时保持根因模式 \(P\)。

### 2.3 阶段一：失败抽象与因果解释

- 输入包括场景数据、故障标签、oracle 结果、关键窗口轨迹、日志/rosbag 等证据。
- 失败抽象模块生成场景摘要、关键窗口记录、oracle 摘要和轨迹证据。
- LLM 被要求输出结构化因果解释，包括失败摘要、关键实体、候选因果交互、推理不确定性和应保持条件；LLM 输出仅视为候选解释，不是 ground truth。
- 根因模式 \(P\) 记录四类信息：
  1. 相关场景实体（自车、交通参与者、水坑、信号灯、路段等）；
  2. 实体间交互（路线阻挡、危险接近、制动距离不足、重规划失败等）；
  3. 应保持兼容的故障症状；
  4. 保持约束（如交通参与者靠近自车路线、任务经过冲突区域、关键窗口附近保留低摩擦区域等）。

### 2.4 阶段二：根因引导生成与规则具体化

- LLM 基于根因模式生成**高层语义变体**，可变化交通参与者位置、速度、路线几何、水坑、天气、任务等，但不直接输出最终坐标或 JSON。
- 规则具体化器负责 schema 对齐、地图/任务字段实例化、交通参与者与水坑放置、天气参数赋值，输出 DriveFuzz 风格候选 JSON。
- 该步骤用于避免 LLM 生成无效坐标、不支持字段、物理上不合理放置或不完整执行参数。

### 2.5 阶段三：执行验证与分类

- **预执行验证**：schema 检查、交通参与者放置检查、任务可行性检查
